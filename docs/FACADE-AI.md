# Facade analysis

The local implementation replaces photo-on-wall preview with Gemini image analysis and procedural facade geometry. One saved image is sufficient to request an improvement of its assigned facade. The guide highlights the selected wall. A candidate is shown before accepting; cancel restores the previous model, and reset clears accepted facade improvements. Images stay in the existing scoped capture store. Accepted compact analysis is stored locally under user, household and address; other devices do not receive it.

POST `/api/energy/vault`, operation `facade-analysis`, reuses the existing function. It verifies the user JWT issuer/audience and household membership before calling Google. The JPEG is sent only on the explicit analysis action, with UI disclosure. No photo/response logging or server photo storage is introduced. `GEMINI_API_KEY` is server-only. Optional `GEMINI_FACADE_MODEL` defaults to `gemini-3-flash-preview`, verified available with a real call on 2026-10-17. The listed `gemini-2.5-pro` returned 404 for this account, so it is not used.

Request image limit is 2.8 million base64 characters, resized to 1600px on the long side. Strict output validation rejects incomplete or low-confidence analyses, unsupported materials/colors, invalid opening coordinates and excessive opening counts. Low-confidence individual openings are removed. Provider calls have a 48-second deadline. A 30-second per-user cooldown is per function instance only; it is not a durable/global spending limit. Provider project quotas must enforce aggregate usage. No database changes.

Facade coordinates are AI estimates in a front elevation, including inferred perspective correction, not measured photogrammetry. Procedural brick/wood surfaces and separate window frames/door geometry receive the existing sun lighting and shadows. The surface height is bounded by the existing roof and terrain samples. Roof, footprint and surrounding geometry are retained. Visual frames do not cast new external shadows; photo-derived uncertain details are not used to claim more accurate solar simulation. This first version does not reconstruct roof details, balconies, transparent wall openings, glazing patterns or hidden sides.

A shared projective transform maps image quads to normalized elevation coordinates in code. Invalid/non-convex quads, incomplete facade bounds, out-of-facade openings and invalid detail data are rejected. Low-confidence openings remain excluded. Wall color is sampled from JPEG pixels inside the traced facade, excluding opening rectangles, highlights, very dark samples and strongly green pixels; it remains sensitive to lighting/occlusions. No user photo is pasted on the wall. Renderer now uses observed muntin placement and individual colors. Survey footprint/height and shadow geometry remain authoritative; exact metric proportions and hidden detail are not recovered from a single picture.

A side-switch action can correct an incorrectly assigned facade. ### Physical capture inspection and partial facade correction

User unlocked the phone. The strict full-wall analysis rejected the existing photo. Opening the app's capture guide showed why: the source picture contains a central door and a large multi-pane glazed opening, but cuts off a window and the wall at the left edge. The original method had mapped this cropped visible segment onto a complete footprint edge, stretching its proportions. No private app file was extracted; the existing in-app thumbnail was inspected via a normal device screenshot.

The revised analysis permits a visible wall section with `coverage=partial`. Its pixel aspect is estimated from the traced wall's opposing edges, using actual JPEG dimensions. The renderer uses a centered local patch rather than filling the complete edge and scales uniformly if it must fit a shorter wall. The UI explicitly labels width and placement as estimates; perspective foreshortening, unseen wall ends and absolute offset cannot be resolved precisely from the crop. Unseen facade parts retain the original geometry/material. New requests send `facadeVersion=3`; older clients get an update message for a partial result instead of silently stretching it. Regression covers partial aspect and full-facade compatibility.
